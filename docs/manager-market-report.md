# 经理的市场报表与数小时计划

已将经理的观察输入改为代码生成的摘要表。经理每次唤醒先读报表，需要解释某项异常或研究新问题时，再通过代码检查相应原始数据。

## 数据流

已完成的分钟 K 线 → 确定性计算 → JSON 数据模型与 Markdown 报表 → 经理比较当前计划并决定保持或调整。

报表随经理唤醒更新，同一分钟内可复用 60 秒缓存。生成报表、保存和比较观察值都不调用模型。不增加经理的唤醒频率，不自动下单，也不替换已有风险订单。

## 报表内容

| 内容 | 含义 |
|---|---|
| 1、4、8、24 小时涨跌 | 指定历史窗口的价格变化，单位 bps，未扣交易成本 |
| 收盘价范围 | 窗口内观察到的分钟收盘最低、最高价 |
| 最大反弹 | 按时间顺序从此前收盘低点到后续收盘高点的最大涨幅 |
| 最大回撤 | 按时间顺序从此前收盘高点到后续收盘低点的最大跌幅 |
| 数据质量 | 缺失分钟、窗口起点滞后、数据年龄和陈旧标记 |
| 较上次变化 | 两次观察的价格变化，以及滚动窗口涨跌值的变化 |

这些是已观察事实，不是预测收益、交易胜率或趋势反转信号。最大反弹和回撤也不是某笔真实仓位的风险测量。价格时间按 Europe/Budapest 展示，表示收盘价何时可获得；只使用该时点已经完成的 K 线。缺口不补值，缺失分钟可能隐藏更极端价格。窗口不足时明确显示不可用。

JSON 版本为 `schema_version: 1`，主要包含 `as_of_utc`、`latest_close_available_at`、`latest_close_age_s`、`stale`、`horizons` 和可选的 `since_previous_report`。行情不可用时保存 `available: false` 与原因，不将旧的成功报表冒充新行情。

## 持久化位置

经理容器中的 `$MANAGER_STATE` 为 `/state`，对应服务器 `~/pixel-office/manager-state`：

- `market-report.json`：最新结构化数据。
- `market-report.md`：经理直接阅读的摘要。
- `market-report-history.jsonl`：追加保存每次更新的观察；缓存命中不重复追加。

经理在共享 REPL 中维护 `mgr_market_plan`，记录判断时间、信息截止时间、方向、持仓视野、依据与不确定性、风险边界、失效条件、执行与退出安排、下次复核及有效期。修订追加到 `mgr_plan_journal`，不覆盖过去的决策。这是经理的工作要求，并非报表代码自行生成的预测或交易计划。

## 2026-10-13 执行与费用修正

当天 10 次付费交易员任务消耗了约 $0.494，却没有成交。经理反复要求可识别性、置信下界和样本量论证，并将验证阶梯当作任何模拟交易的前置门槛。

现已明确区分：小额、预先声明假设与金额风险的模拟实验可以在优势尚未证明时进行；宣称优势或扩大风险仍需要证据。经理用共享 REPL 直接进行已确定的计算和订单执行，不为转达订单、重复晨会或重述同一数学障碍付费。研究必须能改变下一项具体决策；未满足时记录确切缺失的信息和复核时间。

修正保留禁止规则挖掘、未来信息泄漏和从单笔盈利推断优势的要求，也没有复活已经失败的候选。已有空仓计划由经理在下一次决策时重新审查，不由部署脚本自动下单。经理须检查实际持仓参数；交易员遗留的 `max_hold_s=1800` 需要在批准数小时计划时显式指定合适期限。
